# `iwt_53_core` — G2 verification + synthesis (2026-10-19)

> **POST-SYNTHESIS only.** `synth_design` / `report_utilization` / `report_timing_summary`,
> *Design State: Synthesized*. **No** `place_design`, `route_design`, `write_bitstream`, hardware
> manager or board. WNS uses *estimated* routing delays. Simulation is not hardware.

## What was wrong before

`vivado/ip_repo/iwt_53_core/iwt_53_core.v` was **not** a wavelet transform — it was a per-pixel
formula on one register:

```verilog
d_calc <= x - ((x + 0) >>> 1);      // "even" replaced by x and "next even" by 0
s_calc <= x + ((d_calc + 0 + 2) >>> 2);
```

There was no even/odd split, no second sample, no delay line, no edge replication and no second
dimension; `m_axis_tuser` (documented as `00: LL, 01: LH, 10: HL, 11: HH`) was **hard-wired to
`2'b00`**, so the four sub-bands were never distinguishable even in principle. Its testbench
compared nothing. It could not be checked against the reference because it is not the reference's
arithmetic.

## The contract (frozen)

`tools/stego_research/sims/iwt_lifting` — the reference the algorithm is locked to
(`docs/algorithm.md`: DCT-QIM on the 5/3 IWT LL band):

```
even[k] = x[2k]      odd[k] = x[2k+1]      (len even, K = len/2)
d[k]    = odd[k] - ((even[k] + even[k+1]) >> 1)     even[K] := even[K-1]   (replicated)
s[k]    = even[k] + ((d[k-1] + d[k] + 2) >> 2)      d[-1]   := d[0]       (replicated)
```

`>>` is an arithmetic shift (floor), matching the reference's numpy `int32 >>`. The core is the
**1D kernel**; `iwt2d_53` is this kernel on the rows and then on the columns, which is exactly how
the reference defines it (`ll_t, lh_t = iwt1d_53(row_s.T)`, etc.).

Why the core is one line and not one frame: a 512×512 frame's two intermediate sub-bands need
~512 KB, which does not fit this part. Line-at-a-time with a small buffer does.

## Verification (simulation, Icarus)

```
vivado/scripts/run_sim.sh iwt_53_core
  -> iwt_53_core_tb: PASS (12 1D lines bit-exact vs iwt1d_53, 2 frames bit-exact vs iwt2d_53)
```

Two things are checked, and the second is the one that matters:

1. **1D kernel** — 12 lines against `iwt1d_53`, covering the minimum length (2), flat positive and
   negative, a ramp, an impulse, both amplitude extremes, alternating extremes, negative predictor
   and update sums that are not multiples of 2 or 4 (so floor-vs-truncate shows up), a random
   full-range line and a random line at the **maximum supported length (512)**.
2. **2D transform** — the testbench composes two instantiations of the *same* core exactly as the
   reference composes `iwt2d_53` (rows → then columns of the row-low and row-high results) and
   compares **all four sub-bands** against `iwt2d_53`: a 16×16 frame and a **non-square 8×16**
   frame. The non-square frame is deliberate — a row/column swap in the harness does not survive
   it, and that is the usual way a 2D transform is got wrong.

The generator asserts the coefficient widths hold: 18 bits for the 1D outputs, 20 bits for the 2D
result, so the RTL's declared widths are checked, not assumed.

**Mutation-tested** (the testbench must fail on a real defect):

| mutation | errors |
|---|---|
| predictor shift `>>> 1` → `>> 1` (logical instead of floor) | **168** |
| predictor `>>> 1` → `/ 2` (truncate instead of floor) | **52** |
| update `>>> 2` → `/ 4` (truncate instead of floor) | **257** |
| update `+ 2` → `+ 0` (drop the rounding constant) | **327** |
| `d[-1] = d[0]` replication removed from the update | **60** |

**One mutation is deliberately *not* claimed**, because it is not a semantic change: substituting
`>>` for `>>>` in the **update** step leaves the output identical. The two differ by exactly
`2^(acc_width-2)` (= 2^19 for the 20-bit `acc`), which is a multiple of the 18-bit output modulus,
so the low 18 bits — the whole observable result — cannot differ. The vectors do exercise the
negative-`acc` path (101 of 341 coefficient updates have a negative sum that is not a multiple of
4, which is why the `/ 4` mutation fails 257 times); the shift substitution is simply equivalent
under the declared output width. The predictor's `pair_x` is only 18 bits wide, which is why the
same substitution *is* visible there.

## Area: the first synthesis put the line buffers in flip-flops

The first synthesis after the rewrite gave **3137 LUT / 8682 FF / 0 BRAM**. Vivado said why:

```
WARNING: [Synth 8-4767] Trying to implement RAM 'dbuf_reg' in registers.
   Reason is one or more of the following :
   1: RAM is sensitive to asynchronous reset signal. this RTL style is not supported.
```

The line buffers were written inside the main `always @(posedge clk or negedge rst_n)` block, so
they inherited the asynchronous reset and could never be block RAM — 8704 bits of storage became
8682 flip-flops (**24.66%** of the part). A `(* ram_style = "block" *)` attribute alone did not fix
it. Moving the memories into a separate **reset-free** `always @(posedge clk)` block, with the
write enables decoded from the current state, did.

## Real post-synthesis numbers

| | Slice LUTs | Slice Regs | BRAM tiles | DSP | WNS @100 MHz |
|---|---|---|---|---|---|
| buffers as flip-flops | 3137 (17.82 %) | 8682 (24.66 %) | 0 | 0 | +3.666 ns |
| **buffers as RAM (current)** | **158 (0.90 %)** | **150 (0.43 %)** | **1 (2 × RAMB18, 1.67 %)** | **0** | **+3.618 ns — timing met** |

- Tool: `vivado v2026.1`; part `xc7z010clg400-1`; one 10 ns `create_clock`; `synth_1` only.
- Worst path (current): `RAMB18 dbuf` → `s_out` (RAM read → update → output), +3.618 ns slack.
- Throughput: **one line per ~2·len cycles** — loading is `len` cycles, the update pass is `2·K` =
  `len` cycles. A 512-wide line is ~1536 cycles ≈ 15 µs at 100 MHz; structurally the transform is
  applied line by line, so a full frame is many lines (the row pass, then the column pass).
- `LUT as Memory = 0`, `Bonded IOB > 100` in the report are artifacts of synthesising the core as
  top level.

## Interface (changed — nothing integrates this core yet)

```
start + len (even)          -> latch a line
sample_in + valid_in        -> while ready_in
d_valid + d_idx + d_out     -> as each high-pass coefficient becomes known (during loading)
s_valid + s_idx + s_out     -> the low-pass coefficients, in index order
done                        -> one pulse, then IDLE
```

`DATA_WIDTH = 16` in, `DATA_WIDTH+2` out; `MAX_LOG2 = 9` (lines up to 512). Nothing in the repo
instantiates this core yet (the tag pipeline is not built), so the interface is free.

## Honest limits

- **Simulation only.** No place-and-route, no bitstream, no board contact.
- **No inverse (synthesis) core exists.** Perfect reconstruction is demonstrated in the Python
  reference (`iiwt_53`) and not in hardware. Until it is, the hardware chain cannot round-trip.
- The 2D composition is proven **in the testbench harness**, not by an integrated 2D core: the
  product still needs the row/column controllers and the frame buffer plumbing.
- The maximum line length exercised in simulation is 512 (the parameter's limit); the 2D frames
  exercised are 16×16 and 8×16.
- `dwt_2d_core` (Haar, 8-bit clipped outputs, non-checking testbench) was **deprecated** to
  `legacy/dwt_2d_haar/` rather than kept as a second transform in `ip_repo/`.
