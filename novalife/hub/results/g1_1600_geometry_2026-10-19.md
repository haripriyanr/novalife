# G1 — the 1600-downscale geometry defect: root cause, fix, measurement

> **Date:** 2026-10-19. **State:** software only (Python reference). No hardware, no place-and-route,
> no real chat-app send. **Scope:** recovery path (`tools/tag_reference/extract.py`). **The embedding
> is unchanged**, so every marked image and every matrix row about embedding still stands.

## 1. The symptom

On the real de-identified scan (`results/g1_real_image_2026-10-19.md`) the modelled chat-app channel
**2048 → 1600 long edge, JPEG q75** failed, and so did q90, while the *harsher* **2048 → 1280 +
q85** channel recovered. More damage, better result — so the cause had to be geometry, not damage.

## 2. The root cause, measured

A diagnostic (`recover` internals on that one channel, no source change) printed:

```
received 1600x902  declared 2048x1154
true dimension ratio   0.7816 / 0.7812
pilot period (LL)      rows 24.935  cols 25.423   trusted=False
pilot scale            rows 1.5584  cols 1.5889
residual recv_ll - decl_ll*scale  rows -448.2  cols -827.1   (gate needs |.| < 4.0)
=> the gate is VIOLATED
candidates built: 17
   rescale candidate present: False
```

The true pilot period in the *received* LL band is `16 × 0.7816 = 12.5`. The estimator reported
**24.9**, i.e. **the second harmonic (2×)**, and it flagged itself `trusted=False` while doing it.

That was survivable on its own — the payload needs no pilot for a pure resize — except for the next
link in the chain. The "was this axis also cropped?" test was computed **from the pilot period**:

```python
no_crop = abs(recv_ll - decl_ll * snapped_scale(est.rows.period)) < RESIDUAL_MIN_LL   # and cols
```

With a 2× period, `decl_ll * 1.558` is ~450 LL coefficients away from `recv_ll`, so `no_crop` was
`False`, so the **exact size-ratio candidate — the only candidate that uses no pilot number — was
never constructed**. All 17 remaining candidates were built from the wrong period, none could decode,
and the fallback identity map then died inside `read_regions`
(`region 0: ran out of blocks while placing bit 206`), which is why the reported failure looked like a
masking bug.

**One bad number deleted the safety net.** The estimator had already declared itself untrusted, and
the code still let it gate away the only pilot-free path.

Causality was proved before any edit: monkeypatching `candidate_maps` to insert
`rescale recv/decl 0.7816/0.7812` (nothing else changed) gave

```
with the candidate forced in: tag_ok=True exact=True accepted=FORCED rescale ... + fine -0.25/-0.25
  region BER [0.121, 0.102, 0.152, 0.105]
```

## 3. The fix

Two edits in `extract.py`, both recovery-side and both stated in `docs/algorithm.md` §3:

1. **Admit the size-ratio candidate on either of two independent signals**, not on the pilot alone:
   the pilot residual (as before) **or** the two axis dimension ratios agreeing within 1%
   (`AXIS_AGREE_TOL = 0.01`). A rescale multiplies both axes by one factor; an arbitrary crop does
   not. This is evidence that uses no pilot number at all.
2. **Priority candidates take their exact slots first**: `ordered = priority + other[:MAX - len(priority)]`.
   Previously the ordered list was truncated to the first 5, so adding a priority candidate could
   have pushed a pilot-derived candidate out; the safety net must never be crowded out by a guess.
   (For every case with ≤ 5 priority candidates this is an exact no-op on the resulting list.)

The 48-bit tag is still the only verdict, so an extra wrong candidate costs seconds while a missing
right one loses the image. No false-accept exposure is created: the tag gates every attempt.

A permanent regression test was added to `extract.py`'s self-test: it doubles the measured period and
clears `trusted` to simulate this exact mis-lock, then asserts the size-ratio candidate exists and that
a 0.75× resize still recovers exactly.

in **both** versions, so they are damage limits, not this bug, and they are not part of the current
channel set.

## 5. Measurement — nothing that passed regressed

The change can only fire where `no_crop` was `False`. On the phantom covers it was measured directly,
old vs new, on every condition that touches the branch (5 covers × 9 conditions = 45 marks):

| condition | old → new |
|---|---|
| none, jpeg q50, jpeg q40 | PASS → PASS (all covers) |
| resize 0.5x, 0.75x, 1.5x, 2.0x | PASS → PASS (all covers) |
| screenshot-like (0.75x + q80) | PASS → PASS (all covers) |
| crop 25% top-left | fail → fail (all covers) |

**0 verdict changes.** The G1 matrix numbers therefore stand unchanged; no re-run of the 500-mark
matrix is required by this edit.

## 6. What this does and does not buy

- **Buys:** the realistic chat-app profile (long edge 1600, q75/q90) now recovers the tag exactly on
  the real scan, instead of failing while a smaller variant passed.
- **Does not buy:**
  - **The harmonic itself is not fixed.** The estimator still reports 2× the true period on this scan.
    Harmless for a pure resize now, but **crop has no pilot-free fallback**, so crop stays blocked
    until a harmonic guard (or the P2 authenticated lattice) exists. Recorded as open.
  - **The degenerate `read_regions` taint is not fixed.** A candidate aimed at the wrong scale can still
    report `region 0: ran out of blocks`, which misdescribes the reason for a failure.
  - **Crop is still 0/50**; JPEG q40 is still the weak row; real sends are still unmeasured.
